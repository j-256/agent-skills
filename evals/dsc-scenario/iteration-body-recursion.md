# iteration-body-recursion

## Hypothesis

The submittability registry (iteration-submittability-registry) established *which* basket fields `createOrder` requires, but the runnable still rendered them as flat `"<field>"` placeholders the model had to flesh out by hand – leaving two open seams in the deterministic-runnable arc: seam #2 (body *structure* – the nesting shape) and seam #3 (body *values* – the terminal leaf values). A flat placeholder body is not pasteable: a support engineer who pastes it gets a `createOrder` 400 because `paymentInstruments` never carried the nested `paymentCard`, `billingAddress` was an unpopulated stub, and so on – the exact failure the current trophy silently corrected. The fix renders the createBasket body **NESTED and pasteable** (`productItems` / `shipments` / `billingAddress` / `paymentInstruments` with a nested `paymentCard`) directly from the registry's leaf-path list, deterministically, so the customer-facing answer carries a body that submits as-is rather than a skeleton of `<field>` tokens. This closes seams #2+#3 on top of the auth-preamble seam (iteration-auth-preamble-render); the runnable is now deterministic at the auth **and** body boundaries.

## What changed

- **`scripts/build-body.js`** (new) – pure structure assembly. Folds the registry's flat list of nested leaf-path strings (grammar: `foo`, `foo.bar` for object nesting, `foo[].bar` for a single-element array) into a nested JS object, taking each terminal value from an injected `resolveLeafValue` callback. Single-element arrays are deliberate – every submittable-minimum gate is "at least one". Exposes `buildSkeleton` + `deepMerge` (source-wins recursive merge; a nested skeleton array replaces a flat `<field>` placeholder).
- **`_shared/body-values.js`** (new, surfaced into each skill via the `lib/` symlink) – the leaf-value ("persona") resolver: maps a leaf path to its terminal placeholder value so the rendered body reads as populated example data, not `<productId>`-style stubs.
- **`scripts/submittability-registry.js`** – the registry (migrated from the old `submittability.json` in iteration-submittability-registry) now carries a `leaves: [...]` nested-path list per entry alongside the existing `bodyContents` prose. The SCAPI `Basket` entry's leaves encode the nested shape, terminating the payment path at `paymentInstruments[].paymentCard.cardType` (see the drop-one finding below for why `cardType` is the sole card leaf). `elementTypes` pins are test-only (they disambiguate request-vs-response element types at the payment boundary for `test-submittability-schema.js`; the renderer never reads them).
- **`scripts/curl-block.js`** – renders the curated business-rule banner (unchanged framing) and now MERGES the registry-driven nested skeleton on top of the producer's `-d` body via `buildSkeleton` + `deepMerge`. When the nested body carries `${PLACEHOLDER}` values it switches the curl invocation to an unquoted `-d @- <<JSON` heredoc so the shell expands them (a single-quoted `-d` would not), keeping the body valid JSON and pasteable.
- **`evals/dsc-scenario/synthesis-eval.json`** – new fixture `synthesis-scenario-createorder-nested-body` (11th fixture): asserts the customer-facing answer presents the NESTED, pasteable body – `paymentInstruments` → nested `paymentCard` → `cardType`, populated `billingAddress` with `firstName`, public `shopper-baskets-v2` + `createBasket` citations – and EXCLUDES the flat `"field": "<field>"` placeholder shape and the `~/.cache/` citation leak. Customer-outcome assertions only; no tool-path assertions.

## The drop-one card finding (Task 8 – why the shipped card leaf-set is cardType-only)

This is the non-recoverable knowledge the note exists to carry. **Live drop-one on abcd_001 / RefArch (2026-07-11, 14 real orders 00000501–00000514, both SCAPI via SLAS private-client guest + OCAPI guest):** the ONLY required `payment_card` field is `cardType` / `card_type`. `holder`, `expirationMonth` / `expiration_month`, and `expirationYear` / `expiration_year` **each placed an order when omitted** → pared from the registry as above-minimum (they are no longer rendered). Dropping `cardType` **400s** (`InvalidPaymentMethodIdException` "CREDIT_CARD (unknown)"). `masked_number` retained (it is the OCAPI create-body correction citizen – raw `number` is rejected at create with a 400 `UnknownPropertyException`, so the masked form is the runtime-verified card-number field; SCAPI's `Basket` entry does not carry it).

Consequence for this iteration: the SCAPI `Basket` entry's payment leaf is exactly `paymentInstruments[].paymentCard.cardType` and nothing else on the card. The synthesis fixture therefore asserts `cardType` is present in the nested `paymentCard` and **deliberately does NOT assert `holder` or `expiration*`** – asserting a pared field would false-fail against the (correct) rendered body. Any future assertion that references a pared card field is a bug in the fixture, not a regression in the skill.

## Eval results

**Synthesis: `synthesis-scenario-createorder-nested-body` 5/5 strict pass under Sonnet** (`STREAM_EVAL_MODEL=global.anthropic.claude-sonnet-4-6`; `--runs 5 --workers 3 --timeout 300`; 185.8s wall; results at `runs/iteration-body-recursion/results.json`, gitignored). Every run: `pass=True`, `failed_asserts=0`, `retries=0`, `contaminated=False`, `first_tool=Skill` / `first_skill=dsc-scenario` (triggered correctly), ~88–101s each. All customer-outcome assertions matched on the guest-shopper `createOrder` query:

- `paymentInstruments[\s\S]{0,300}paymentCard` – the nested paymentCard the flat-placeholder body never carried (the createOrder-400 discriminator) is present.
- `paymentCard[\s\S]{0,200}cardType` – the nested card carries `cardType` (the live-verified sole card leaf).
- `billingAddress[\s\S]{0,120}firstName` – billingAddress rendered as a populated nested object, not a `<billingAddress>` stub.
- public `shopper-baskets-v2` + `createBasket` citation anchors matched (versioned slug, no false-fail).
- EXCLUDES matched: no flat `"productItems": "<productItems>"` structured-field placeholder; no `~/.cache/` citation leak.

Offline determinism check before the run confirmed the fixture asserts real behavior: a real `createOrder` plan rendered via `scenario.js` (bridge-pick `createBasket`) produces a body satisfying all four positive regexes and none of the excludes – so a failing assertion would be a genuine Sonnet-composition signal, not a stale-regex artifact.

The eval was run against a single-fixture extract (`runs/iteration-body-recursion/nested-body-only.json`) rather than the full 11-fixture `synthesis-eval.json`, to isolate the new fixture and sidestep the known `add-coupon-checkout` cache-spelunk wall-clock timeout (roadmap parked TODO `/c/TODO-scenario-cache-spelunk-adherence.md`) that would `aborted_on_timeout`-bail a full-suite run before reaching this fixture. The fixture itself is committed into the tracked `synthesis-eval.json` (11 fixtures).

## Surprises / rejected alternatives

- **The card shape was NOT what the registry's prose minimum implied.** The submittability prose (iteration-submittability-registry) named "a payment instrument (e.g. paymentMethodId CREDIT_CARD)" without pinning the card sub-shape; a naive nesting would have rendered `holder` / `expirationMonth` / `expirationYear` as "obviously required" card fields. Task 8's drop-one disproved that – only `cardType` is enforced – which is precisely why live verification (not spec- or intuition-derived nesting) was non-negotiable for the leaf set. Encoding the intuited card fields would have shipped a body carrying three fields the gate does not require.
- **Single-element arrays over representative multi-element bodies.** `build-body.js` renders one element per array (`foo[].bar` → `{foo:[{...}]}`) because every submittable gate is "at least one"; a multi-item body would be larger and no more pasteable.
- **Heredoc-only when placeholders are present.** `curl-block.js` switches to the unquoted `-d @- <<JSON` heredoc only when the nested body carries `${PLACEHOLDER}` values needing shell expansion; a single-quoted `-d` body would emit the literal `${...}` tokens. The bodyContents-only path (no nested leaves) keeps its prior flat rendering.
