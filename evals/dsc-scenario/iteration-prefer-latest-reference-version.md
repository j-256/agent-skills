# iteration-prefer-latest-reference-version

## Hypothesis

Prefer the latest version of a versioned DSC reference by default (e.g. `shopper-baskets-v2` over `shopper-baskets`) while honoring an explicitly-requested version. Filed as the "Follow-up surfaced" in `iteration-runnable-jq.md`: a createorder run there drifted to `shopper-baskets-v2` nondeterministically, exposing that the skill had no version-selection logic.

Initial framing (from the brief): "prefer latest" is a *local resolver rule* over data already on disk -- the `_landing/<area>.json` manifest enumerates both versions side by side, so no re-scrape is needed; read the landing, pick the highest `-v<N>` sibling unless a version was named explicitly.

That framing was half right. The landing *does* enumerate both versions -- but only when it exists, and it often doesn't (see "Root cause" below). The investigation is what turned a "small local resolver rule" into a foundation fix plus a composition rule.

## Versioning-convention survey (all 23 cached area landings)

(Note: "23 area landings" = the 23 distinct product areas cached under `_landing/`; not to be confused with the "56-entry catalog" mentioned later, which is the number of references *within* the single commerce-api area.)

Keyed the rule on the id pattern, not the title, after surveying every cached landing:

| Case | id / title | Handling |
|---|---|---|
| `shopper-baskets` / `shopper-baskets-v2` | titles "V1"/"V2" | The target pair -- clean `<base>-v<N>` hyphen siblings |
| `bot-api-v5` (einstein-bot) | `-v5`, no unsuffixed sibling | Must NOT be "downgraded" to a nonexistent `bot-api` |
| TMF family (communications) | version in *title* (`tmf620`), hyphenless in id (`tmf621v4`), id/title mismatch (`tmf651v5` titled "v4"), and `tmf621` is the **Outbound** variant -- a *different API*, not a base version | A loose pattern would wrongly group these |

No reference carries a `version` field; versioning lives in the id suffix and/or title. Conclusion: group on the hyphen-anchored id pattern `^<base>-v<N>$`, base treated as implicit v1. This isolates the basket pair and touches nothing else -- TMF ids don't match (no hyphen before the version, or version only in title), and `bot-api-v5` has no base sibling to prefer. `shopper-baskets` is the only pair in the cache where the rule changes anything today.

## v1 vs v2 endpoint diff -- newest is a clean superset

All 37 endpoint slugs are identical between `shopper-baskets` and `shopper-baskets-v2`; `addCouponToBasket` is path- and scope-identical across both. No v1-only operation, so "newest wins" needs no carve-out. (V2 adds temporary-basket behavior/fields, not new operations.)

## Root cause -- the missing landing write (NOT model discretion)

The first diagnosis from eval data was "the model runs the exposer, sees `latest: shopper-baskets-v2`, then reverts to the prompt's bare slug and cites V1 -- a threading bug." That was WRONG, and the correction is the central finding of this iteration.

Re-investigation (transcripts + a clean-room scrape) showed:

- The exposer reads `~/.cache/dsc-scrape/_landing/<area>.json` to find version siblings. **A per-reference scrape (`runReferenceRoot` in `scrape.js`) never wrote that landing** -- only whole-area scrapes (`runAreaLanding`) did. On a per-reference cache -- the common path, and exactly what the eval's isolated temp HOME builds when the model scrapes one reference -- `_landing/` is absent, so `resolveVersions` falls into its single-version no-op branch and returns `hasMultipleVersions: false`.
- So the model wasn't ignoring the exposer. It ran the exposer, was told (incorrectly) "only one version exists," and correctly didn't bump. Proven directly: in a *passing* createorder run the exposer call returned `latest: shopper-baskets`, `hasMultipleVersions: false` -- that run only reached V2 because the model independently poked at `shopper-baskets-v2` by hand, not because the exposer worked.
- Corollary: the `DSC_CACHE_TTL_MS=999...` "offline" guard was moot. The isolated cache starts empty, so every run does a live `developer.salesforce.com` scrape regardless of TTL -- the real source of the wall-clock timeouts and throttling seen in the early runs. The brief's "no re-scrape needed" premise held only for the dev cache, where whole areas had been scraped and the landing happened to exist.

Clean-room proof: `node scrape.js ".../references/shopper-baskets" $TMP` wrote the `shopper-baskets/` dir but no `_landing/` dir, and `shopper-baskets-v2` appeared nowhere in the resulting cache.

## What changed

**`scrape.js` `runReferenceRoot` -- persist the area landing (commit `ffdd4c9`).** The function already calls `fetchReferencesPage` + `parseCatalog` and holds the full 56-entry area catalog (including both basket versions, with `{id, title}`) in memory to locate the requested reference -- it just discarded it. Now it writes `_landing/<area>.json` (write-if-absent/stale, so it never clobbers a fresher whole-area landing), mirroring `runAreaLanding`'s `kind: 'area-landing'` shape. +20 lines, additive only: it writes a manifest whole-area scrapes already produce, so no existing consumer's behavior changes. Independently verified live -- scraping *any* commerce-api reference (even `shopper-orders`) now makes the whole area's version siblings visible, so the exposer reports `shopper-baskets -> latest=shopper-baskets-v2` and the resolver's `landingsForReference('shopper-baskets-v2')` resolves. This fix benefits every landing consumer (resolve-cache, the exposer), not just prefer-latest.

**`reference-versions.js` -- the deterministic exposer (commits `a591cc0`, `ce5bf91`).** Dual-mode lib + CLI (mirrors `scrape.js`'s `require.main` shape), beside `resolve-cache.js`, reached by dsc-scenario through its `lib -> ../_shared` symlink. `resolveVersions(cacheRoot, id, {area?})` returns `{requested, requestedIsVersioned, latest, versions:[{id, version, basePath}], hasMultipleVersions}` -- facts only, never a decision; provenance ("user pinned v1") stays with the model. Surfaces `basePath` so callers don't conflate the id `shopper-baskets-v2` with the REST path segment `shopper-baskets/v2`. No-op single-entry shape for unversioned/uncached ids. Unit-tested (`test-reference-versions.js`): basket pair -> v2; unversioned -> no-op; `bot-api-v5` (suffixed, no base) -> itself; explicit `-v2` -> `requestedIsVersioned:true`; malformed args throw `VersionResolutionError`.

**`scenario.js` -- the deterministic bump (commit `06b85ff`), and the SKILL.md rule it replaced (`23c2980`).** The first attempt was a SKILL.md prose rule (sibling to "Stay on the user's chosen API family"): have the model run the exposer at resolve-target and use `latest`. Eval showed that is *unreliable* -- the model often runs the exposer on a cold cache (before scraping, so the landing isn't written yet -> exposer reports one version) and cites V1, or runs it and reverts to the prompt's bare slug. Prose can't fix an ordering the model controls. So the decision moved into code: `scenario.js` already runs `scrapeRefresh` as step 1 (which now writes the landing, via the foundation fix), so immediately after it calls `resolveVersions` and -- unless the caller passes `pinVersion` -- bumps the reference slug to `latest`, re-scrapes the bumped reference, and threads the bumped slug through resolve/walk/compose/cite. Citations and the runnable's `/checkout/shopper-baskets/v2/` prefix then come out V2 deterministically regardless of model step-order. `resolveVersions` stays a pure offline reader. The SKILL.md rule simplified to its one residual judgment: the model passes `pinVersion: true` only when the user explicitly names a version (a `-vN` in a pasted URL, "shopper-baskets v1", an operationId tied to a version); otherwise the bump picks latest. New `scenario.js` integration tests (a `ver-area`/`verref`+`verref-v2` fixture pair) assert the bump fires for a bare reference and is suppressed under `pinVersion`; a separate area was used so the existing unversioned `tiny-ref` tests stay no-op.

**`synthesis-eval.json` -- one positive assertion (commit `b15783c`) + a retuned federated exclude.** The positive: `final_text_matches` on `references/shopper-baskets-v2` in the createorder fixture -- proves the plan defaulted to and cited V2 when the prompt pinned no version. Deliberately NOT a bare-`shopper-baskets` exclude -- `shopper-baskets` is a substring of `shopper-baskets-v2`, of `sfcc.shopper-baskets-orders.rw`, and of the REST path, so an exclude would false-fail every correct answer. The retune: the `registered-federated` fixture's `authenticateCustomer` exclude was a bare-token pattern, firing on a federated plan that merely NAMED `authenticateCustomer` in a B2C-contrast sentence. Narrowed to `meta=authenticateCustomer|/oauth2/login` -- matches the *invocation* form (citation slug or login path), not the bare noun. Important nuance discovered while doing this: the bare-noun contrast is NOT actually "fine" -- naming the B2C path on a federated plan, even as a contrast, is a (milder) violation of the same "Don't narrate the alternatives" rule. So the split is deliberate: the **assertion** is the automated floor (catches the worst form -- an actual `/oauth2/login` invocation or `?meta=` citation -- without false-positiving on every incidental noun), while the **SKILL.md prose** (strengthened this iteration, see below) forbids the mention entirely. Assertion = floor that won't misfire; prose = the fuller bar.

## Results

Sonnet 4.6, harness `7a049a3`, `--profile isolated`, `--timeout 600`, 7 fixtures x5. (Aside: 0 retries / 0 timeouts across all 35 -- the long per-run elapsed, 107-398s, is genuine compose time for full auth+basket+checkout chains, not API throttling; an earlier 300s-timeout run had hit the backstop purely because the ceiling was too low for these compositions.)

**The deterministic bump validated prefer-latest end-to-end.** All four basket-version fixtures strict-pass 5/5: `createorder-basketid-threading` (carries the v2 assertion), `add-coupon-checkout`, `registered-silent`, `registered-b2c-primed`. Independently confirmed: each cites `references/shopper-baskets-v2` and uses the `/checkout/shopper-baskets/v2` runnable prefix. The decisive contrast: `registered-silent` and `add-coupon-checkout` cited *V1* in the pre-lever-2 run (model ran the exposer cold, before scraping); under the `scenario.js` bump they are V2 every run. `am-admin-orders` 5/5 (version no-op, AM-routed). `ocapi-submit-basket` is a version no-op too (its reference is `ocapi-shop-baskets`, no `-v` sibling).

**Two non-version fixtures landed 4/5, both correctly:**
- `ocapi-submit-basket` 4/5: run-2 failed the OCAPI path-notation match (`/dw/shop/v\d+`) because the model emitted a templated `v{ver}` instead of a concrete version segment. Not a version issue and not a false positive -- the assertion correctly wants concrete OCAPI notation; 4/5 runs produced it. Single-run model variance; left as-is per "don't tune red to green."
- `registered-federated` 4/5 (before the prose fix): a confirmation run (federated x5, after the exclude retune) was 4/5 -- run-4 failed because the model added a forbidden *"if your instance is not federated, `authenticateCustomer` (`POST /oauth2/login`) is the alternative"* aside, **inside an otherwise-correct note explaining why the federated step needs a browser**. SKILL.md already prohibited the footnote (the "Don't narrate the alternatives" rule + the `registered-federated` line under "IDP framing"), but the model rationalized the mention as part of explaining the headless-capture limitation -- a gap the existing rules didn't explicitly close. The retuned exclude correctly caught it (real rule violation, not a false positive). Rather than defer this as a separate iteration, it was fixed here: SKILL.md's `registered-federated` rule was strengthened to forbid naming `authenticateCustomer`/`/oauth2/login` *anywhere* in a federated plan -- "especially inside the browser-step explanation" -- and to explain the browser necessity using only the federated mechanism, never the B2C contrast. Re-evaluated federated x5 after the fix: **5/5 strict, 0 failed asserts** (`results-federated-fix.json`). Independently confirmed across all 5 transcripts: zero `/oauth2/login` or `?meta=authenticateCustomer` (the invoked form), correct `authorizeCustomer`+`hint=` flow in every run. Prose alone closed it -- but only because the rule was aimed at the model's *rationalization* (naming the B2C path while explaining why the browser step is needed), not just repeating the existing prohibition.

Net: the prefer-latest deliverable is strict-green on every fixture it touches. The one model-variance slip (ocapi `v{ver}`, 1/5) is left as-is per "don't tune red to green." The federated alternative-narration flake -- pre-existing, unrelated to versions, surfaced by the extra federated runs -- was fixed in-iteration via the strengthened prose rather than punted.

## Surprises

- **The "threading bug" was a missing-file bug.** Two rounds of eval data looked like model unreliability (~75% v2, nondeterministic) and nearly drove a SKILL.md-prose arms race. The real cause was that the exposer's input file (`_landing/<area>.json`) didn't exist on a per-reference cache, so the exposer truthfully reported "one version" and the model correctly obeyed. The fix was upstream of both the model and the exposer. Lesson: when a deterministic helper gives a "wrong" answer, verify its *inputs exist in the environment under test* before concluding the model is ignoring it.
- **The eval cache is not the dev cache.** The brief's "no re-scrape needed -- the landing already has both versions" was true on the dev box (whole areas scraped) and false in the eval's isolated per-reference HOME. A premise that holds in the authoring environment can silently fail in the test environment; the clean-room scrape into a fresh temp cache is what exposed it.
- **An eval spawn edited a tracked source file.** A `claude -p` synthesis spawn, while running the skill, hit a cache-layout mismatch and edited the repo's `walk-types.js` to "fix" it (the isolated profile isolates HOME/skills but not the repo cwd). Reverted -- not part of this iteration -- but it surfaced a real latent bug (filed separately): `producedTypes()` expects an OAS-keyed `responses` layout but the live cache is index-keyed, so local `walkTypes()` finds zero edges; its test passes only because the fixture drifted to the old layout. Masked in practice because the skill hand-walks / sub-agent-walks rather than relying on local `walkTypes`.

## Follow-up surfaced

The broader ask -- "every invocation runs deterministic scripts rather than the model analyzing JSON" -- is wider than version selection. Two other model-driven cache-traversal loci remain in a scenario run: (a) natural-language goal -> operationId (fuzzy title/Summary matching across references), and (c) confirming which references are involved. This iteration's `reference-versions.js` closes locus (b) only. A dedicated `deterministic-cache-exposer-audit` iteration should inventory every place the model still hand-reads cache JSON and replace each with a deterministic exposer (or decide, with reasons, that a locus must stay model-driven -- fuzzy NL matching is hard to make deterministic and to eval cleanly). Deferred to keep this iteration scoped.

Two harness/infra follow-ups also surfaced and are tracked outside the repo (not cited here by external path, per repo policy): a per-fixture filter for the eval harness (re-running unaffected fixtures wastes spawns), and the `walk-types.js` responses-layout drift above.
