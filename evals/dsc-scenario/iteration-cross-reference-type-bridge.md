# iteration-cross-reference-type-bridge

## Hypothesis

Second brick of the "scripts traverse, model judges" push (brick 1 was `iteration-blind-ingress-cache-accessor`; its "Follow-up surfaced" named this work: "Cross-reference walk consumes `siblings()`; that's where createOrder's target-only plan gets fixed"). A target whose request body is a resource *produced in another reference* – the canonical case is `createOrder`, whose body is a prepared `Basket` produced by `shopper-baskets-v2.createBasket` – produced a structurally incomplete plan. `scenario.js` walked only the target's own reference (`shopper-orders`), found no in-reference producer of the `Basket` body, and emitted a plan that simply assumed a `basketId` already existed. The model, handed an incomplete structural plan, fell back to reading the cache by hand to reconstruct the missing producer step.

The fix is a deterministic cross-reference "type bridge": when the target's body type has no producer in its own reference, `scenario.js` enumerates the area's reference siblings, scans them for operations that produce that type *from nothing*, and surfaces those as `bridgeCandidates`. The model makes exactly one judgment – pick the canonical create from the candidate set – then re-invokes `scenario.js` with `bridgeProducer:"<slug>"`, and the second pass composes the full cross-reference plan deterministically (producer step + bridge edge + per-reference runnable prefix). Everything except the producer pick is structural.

## The verified problem

The brick-1 synthesis transcripts (`iteration-blind-ingress-cache-accessor`) showed the model cat-spelunking `createOrder`: with a target-only structural plan that named no `Basket` producer, the model went looking through the cache by hand to figure out where `basketId` comes from, then hand-assembled the producer step in prose. Brick 1 closed the *cache-orchestration* half of cat-spelunking (the accessor reads the cache for the model), but explicitly scoped itself to output-neutrality and left the structural gap open: "It does NOT prove createOrder's structural plan improved (that's the next brick)." This brick removes the *reason* the model reached into the cache – the plan now arrives with the producer already discovered and the bridge edge already drawn, so there is nothing left to reconstruct by hand.

## What changed

Eleven commits, each a brick that composes into the two-pass bridge. In dependency order:

- **Per-node `reference` field in walk-types (`cc11ad4`).** `walkTypes` nodes gained a `reference` field so a graph can carry nodes from more than one reference. Prerequisite for everything downstream: a cross-reference plan is a graph whose nodes don't all share one reference, so the node has to remember which reference it came from. Additive – single-reference walks just tag every node with the one reference.

- **`dominantPathId` structural threading-field signal (`438ce10`).** A pure reader over a reference's endpoints: count each *required, non-universal* path parameter across all of the reference's operations and return the most common one. For `shopper-baskets`/`shopper-baskets-v2` that is `basketId`. This is the structural answer to "what field threads the producer's output into the consumer" – no prose-reading, no model judgment. `organizationId`/`siteId`-type universal params are excluded so they can't win.

- **`producersOfType` warm-spec scan with from-nothing filter (`bdd6fc8`).** Given a type name and a set of references, scan their warmed specs for operations whose response produces that type, then *drop any operation that requires the type's own dominant id as an input* – the "from-nothing" filter. An op that already needs a `basketId` to run can't be what *creates* the basket. This is the structural half of producer discovery: it narrows "everything that touches a Basket" down to "everything that produces a Basket without first being handed one."

- **Body-type bridge surfaces cross-reference producer candidates (`78ccd2f`).** `walkTypes` now detects when the target's body is a named type with no in-reference producer and, given warmed `siblingRefs`, calls `producersOfType` against them to build a `bridgeCandidates` array. It also annotates the target node's required-input with the structurally-derived threading field (or `needsNaming` when `dominantPathId` finds none). This is the discovery output the model consumes.

- **Multi-reference compose loads each step from its own reference (`2679dbe`).** `composePlan` previously assumed every step lived in one reference; now each step is loaded from its own node's `reference`, so a plan spanning `shopper-baskets-v2` (producer) and `shopper-orders` (target) cites each step against the correct reference's spec URL.

- **Deterministic per-reference URL prefix in runnable (`40748dc`).** The runnable's cURL prefix is emitted per-step from each reference's `basePath` (`/checkout/shopper-baskets/v2/...` for the producer, `/checkout/shopper-orders/v1/...` for the target), so a multi-reference runnable threads the right path segment per call without the model reconstructing it. This is what let the now-deterministic prefix prose come *out* of SKILL.md (see next).

- **Two-pass cross-reference bridge discovery + prewarm in `scenario.js` (`f3f20f5`).** The orchestration. When the target's body type has no in-reference producer, `scenario.js` enumerates family siblings from the landing the accessor guaranteed, NARROW-prefetches the name-match candidates and scans, and only WIDEN-prefetches the whole family if narrow found nothing. Pass 1 (no `bridgeProducer`) returns the target-only plan plus `bridgeCandidates`; pass 2 (`bridgeProducer` supplied) warms the chosen producer's reference, grafts its node + the bridge edge (threading field from the *chosen* producer's `dominantPathId`), and composes the full plan.

- **Lock the two-pass contract in tests (`9ad0dce`).** Integration tests assert pass 1 returns the target-only plan and the candidate array (no producer step yet), and pass 2 composes the producer step without re-emitting the candidate array – the contract the model depends on.

- **SKILL.md two-pass rule + drop now-deterministic prefix prose (`fc290cd`).** Added the "Cross-reference bridge (two-pass)" rule under Flow: pick the single canonical *create* from `bridgeCandidates` (the op that builds the resource fresh, not `mergeBasket`/`transferBasket` which presuppose an existing basket), re-run with `bridgeProducer`, don't hand-write the producer step, don't list alternatives in the plan. Removed the old prose that had the model reconstruct the runnable's URL prefix by hand – that became deterministic in `40748dc`, so the instruction was deleted rather than left as dead guidance.

- **Apply prefer-latest to cross-reference bridge producer discovery (`801016f`).** The fix the real-cache check caught. A producer type can be published in several version families – the Basket producers live in BOTH `shopper-baskets` and `shopper-baskets-v2`. Without filtering, `siblingRefs` surfaced every version's producers (a v1 duplicate of each v2 op) and pass 2 could graft the superseded version. `scenario.js` now filters `siblingRefs` to the latest version of each family (honoring `pinVersion`), the same prefer-latest rule the primary target already got in `iteration-prefer-latest-reference-version`. `siblingRefs` is the single chokepoint feeding both passes, so one filter fixes both.

- **Guard the single-version bridge-producer survival path (`1768444`).** A regression test: when a producer family has no newer version, the prefer-latest filter must *keep* it (not drop everything). Locks the boundary the `801016f` filter could have over-applied.

## The structural-vs-reasoning split

The push's thesis is "scripts traverse, model judges." This iteration is the sharpest test of it so far, because the cross-reference bridge looks like it needs reasoning at three points – and two of the three turned out to be deterministic:

- **Discovery (which sibling reference produces the body type) – structural.** `producersOfType` scans warmed specs and the from-nothing filter drops anything that requires the type's own id as input. No prose-reading; the producer set falls out of the type graph.
- **The threading field (what links producer to consumer) – structural.** `dominantPathId` reads it off the producer reference's own endpoint shape: the required path param shared by the most operations in that reference *is* the resource's id (`basketId` for the basket references). It is not read from prose, and it is not a model guess.
- **The runnable's URL prefix – structural.** Each step's prefix is emitted from its reference's `basePath` (`40748dc`), so a multi-reference runnable threads `/checkout/shopper-baskets/v2/...` then `/checkout/shopper-orders/v1/...` without the model reconstructing either. This is what let the prefix prose come out of SKILL.md entirely.

The one judgment that genuinely stays the model's: **which candidate is the canonical create.** The from-nothing filter cannot make this call, and the reason is concrete (see Surprises): `createBasket`, `mergeBasket`, and `transferBasket` *all* survive it – none takes a `basketId` path param, so structurally all three "produce a Basket from nothing." The distinction between them is semantic – `mergeBasket`/`transferBasket` presuppose an existing basket the shopper is merging or transferring *from*; `createBasket` builds one fresh – and that lives in the operations' meaning, not in any field the walk can read. So the model picks, from a structurally-narrowed set of three, the one canonical create. The two new assertions guard exactly this seam: that the pick is `createBasket` (canonical-producer) and that the model doesn't paper over the single-create design by decomposing basket prep into a multi-step sequence (over-decomposition).

## Assertions added this iteration

Two `final_text_excludes` on the `synthesis-scenario-createorder-basketid-threading` fixture, both step-form anchored so a correct prose mention can't false-fail (the mention-vs-mechanism discipline):

- **Canonical-producer.** `mergeBasket`/`transferBasket` must not appear *as a numbered plan step*. The shipped pattern anchors on the bold step header (`**Step N ... <op>`) or the invocable `<op> (POST ...)` render – not a bare `Step N` prose cross-reference. (The brief's first-cut pattern was `step\s*\d[^\n]*<op>`; it was retuned during this iteration's eval after a false-fail – see Results and Surprises. The retune is a regex-over-strictness fix, not a red-to-green tune: the model's behavior was correct.)
- **Over-decomposition.** `addItemToBasket`/`addPaymentInstrumentToBasket`/`updateShippingAddressForShipment`/`updateBillingAddressForBasket` must not appear *as numbered steps*. A prepared basket carries items/shipping/payment in the single `createBasket` body; describing that body's contents in prose is fine, expanding each into its own API step is the over-decomposition this guards.

Both are anchored on the invoked/step form, never the bare op noun – an answer that describes the basket body's contents, or names `mergeBasket`/`transferBasket` as rejected alternatives in prose, must (and does) pass.

## Surprises

- **The threading field turned out structural, via the dominant path id.** Going in, "what field threads the producer's output into the consumer's body" read like a prose-reading task (read the `createOrder` body description, find that it wants a `basketId`). It isn't: the required path param shared by the most operations in the producer's own reference *is* that resource's id. `dominantPathId` reads `basketId` straight off `shopper-baskets-v2`'s endpoint shape. A locus that looked like model judgment collapsed to a one-function count over the spec.
- **The URL prefix turned out deterministic, via `basePath`.** The runnable's per-reference prefix (`/checkout/shopper-baskets/v2/...` vs `/checkout/shopper-orders/v1/...`) had been a SKILL.md instruction telling the model to reconstruct it. Once each step is emitted from its reference's `basePath`, the instruction was not just unnecessary but a liability (a place the model could drift). It was deleted from SKILL.md (`fc290cd`), not merely deprecated – the deterministic emitter is the contract now.
- **The fewest-prerequisites tiebreaker was provably wrong.** An early design instinct was to disambiguate the producer candidates structurally by picking the one with the fewest required inputs ("simplest producer wins"). That is wrong: `createBasket`, `mergeBasket`, and `transferBasket` all take the same universal path params and all survive the from-nothing filter, so "fewest prereqs" doesn't separate them – and worse, if it did separate them it would separate on an irrelevant axis (input count), not the relevant one (does this op build the resource fresh, or derive it from an existing one). The disambiguation is irreducibly semantic, so it stays the model's single judgment rather than being faked with a structural proxy. This is why the canonical-producer assertion exists: to guard a seam that *can't* be closed structurally.
- **The real-cache check caught the prefer-latest-on-bridge gap the unit tests missed.** The bridge discovery's unit/integration tests passed while the producer candidate set silently included v1 duplicates – the Basket producers are published in BOTH `shopper-baskets` and `shopper-baskets-v2`, and `siblingRefs` surfaced both versions' ops. The fixtures didn't model a versioned producer family, so the tests were green on a candidate set that, on the real cache, could let pass 2 graft the superseded v1 producer. Running against the live commerce-api cache exposed it; the fix (`801016f`) applies the same prefer-latest filter the primary target already had, at the `siblingRefs` chokepoint that feeds both passes, with a survival-path guard (`1768444`) so a single-version family isn't dropped. Same lesson as the fixture-conformance traps in prior iterations: a fixture that doesn't model the real shape makes the test lie.
- **The new canonical-producer assertion false-failed on the model's *correct* behavior, on the first run.** Run 1 of the standalone createorder eval picked `createBasket`, didn't over-decompose, cited v2 – a correct plan – and still failed the canonical-producer exclude. The cause was the brief's loose first branch (`step\s*\d[^\n]*<op>`) bridging an incidental `(Step 2)` cross-reference inside an explanatory blockquote across to the rejected-alternative nouns the model correctly named ("the basket must be created fresh – `transferBasket` and `mergeBasket` both presuppose an existing basket"). Three of the four *passing* runs named the same alternatives in the same way; they passed only because their phrasing didn't put a `Step N` token on the line. Naming the rejected alternatives is the *ideal* mention-vs-mechanism behavior, so this was a regex-over-strictness false-fail, not a skill defect – fixed by anchoring on the bold `**Step` header marker (prose cross-references write `(Step 2)`, not `**Step 2**`) and bounding the `<op>`→`(POST` gap to backtick/space/colon only. The lesson is the one the repo's eval discipline already encodes: a step-form-anchored exclude has to anchor on the *step-header syntax*, not on the mere co-occurrence of a step number and the noun on one line.
