# iteration-auth-preamble-render

Move the auth token-acquisition preamble out of model-composed SKILL.md prose into the deterministic renderer, so the whole `## Run it` runnable -- token legs + `ACCESS_TOKEN=$(...)` capture included -- is emitted by `scenario.js` and the model relays it verbatim. Closes seam #1 of the deterministic-runnable arc (the other two seams -- nested body structure + leaf values -- are the next sub-project). Folds in the two cleanups that converge here: the top fill-in block (referenced-minus-assigned scan, correct-by-construction only once auth renders) and snake `NAMES_LIKE_THIS` var naming.

## What the diff can't carry

### The fill-in block's correctness is a consequence of rendering auth, not an independent feature
The top fill-in block derives its var set by scanning the fully-composed runnable for referenced (`${VAR}`) minus assigned (`^VAR=`) names (`scanFillInVars`). This is correct-by-construction ONLY because the auth preamble now renders: `ACCESS_TOKEN` is *assigned* by the token exchange / header capture, so referenced-minus-assigned excludes it -- the user is not told to supply a value the script computes. Before this iteration, auth was model-prose the scan couldn't see, so `ACCESS_TOKEN` would have wrongly landed in the fill-in block. This is why the fill-in block could not have shipped as its own iteration ahead of auth rendering; the two are one change. The load-bearing subtlety the Task 6->7 handoff turned on: `scanFillInVars`'s assigned-regex is `/^([A-Z0-9_]+)=/gm` -- column-0 only. Every producer/auth capture the renderer emits (`*_RESPONSE=`, jq captures, `ACCESS_TOKEN=`, `AUTH_CODE=`, `CODE_VERIFIER=`) MUST be at column 0, no indentation, no `export ` -- an indented capture would leak back into the fill-in block. curl-block structurally cannot indent preamble lines (it does `body.push(...preamble.lines)` untransformed), so the property holds, but it is a real constraint, not an accident.

### Live grounding: two rendered preambles minted real tokens
The opt-in `DSC_LIVE_TESTS=1` probe (`test-auth-render-live.js`) built preambles from the real resolver, substituted sandbox creds, EXECUTED the rendered bash, and asserted a token minted -- the layer that historically caught the AM `.net`->`.com` host defect and the SLAS-vs-OCAPI-native misconception (text assertions hid both). Result: AM app-token and OCAPI-native `customers/auth` guest JWT (944-char) both minted `TOKEN_OK` against the RefArch sandbox -- the emitted bash shapes are correct against the LIVE API, not merely fixture-shaped. NO renderer defect was found: both initial live failures were PROBE env-mapping issues, correctly diagnosed without touching `b2c-auth-render.js` -- (a) the `am` branch mints a SCAPI-Admin token, so it needs `CLIENT_ID_SCAPI`, not the OCAPI client (the OCAPI client returned `invalid_scope`, NOT `invalid_client` -- valid auth, missing role, which itself proves the request shape is right); (b) `customers/auth` is served from the instance host, not the SCAPI shortcode edge. SLAS-guest self-skipped (no public client / redirect URI provisioned) -- best-effort. The probe's honesty is provable: its first-run `TOKEN_EMPTY`/404 failures show the success gate (`[ -n "$ACCESS_TOKEN" ] && [ "$ACCESS_TOKEN" != "null" ]`) rejects errors rather than greenwashing them.

### The single ${BASE_URL} collapse fixed a latent trophy defect
The two shipped trophies disagreed on the SLAS host: `scenario-createorder-prereqs.md` split it into a separate `${SLAS_BASE_URL}` whose example value was the `.dx.` instance host (wrong for SCAPI checkout, which is served from `<short-code>.api.commercecloud.salesforce.com`); `scenario-add-coupon-checkout.md` used one `${BASE_URL}` correctly. The renderer emits a single `${BASE_URL}` for both SLAS and checkout (same host), which is not just simpler but eliminates the createorder trophy's latent host error. `ORGANIZATION_ID` repeats at most twice (once in the SLAS basePath constant, once per checkout call) -- unavoidable and cheaper than a second base var. AM's `account.demandware.com` is a distinct absolute host, untouched.

## Surprises / rejected alternatives

### The migration-exclude fixture was mis-anchored (noun co-occurrence, not advocacy)
`synthesis-scenario-ocapi-submit-basket` failed 1/5 runs (run 3), and the miss was a fixture bug, not a skill regression. Assertion [3] excluded `(migrate|migration).{0,40}...ocapi.{0,40}...scapi` with `because: "must not propose OCAPI->SCAPI migration"`. It fired on a factually-CORRECT sentence the model added because the user's own query ends "is the basket -> order chain the same as SCAPI?": *"Migration direction is one-way (customers move off OCAPI onto SCAPI, not the reverse) -- mentioned only as background; this plan stays in OCAPI per your question."* The model did not PROPOSE migration -- it stated the one-way direction (matching the OCAPI->SCAPI migration-direction memory) while explicitly declining to advocate. Proof the pattern was phrasing-fragile: run 2 PASSED while mentioning migration ("SLAS is a migration-forward alternative") because its word order dodged the char windows. This is the certainty-layer lesson exactly -- an exclude that must fire on a wrong claim while a correct answer legitimately names the same nouns must anchor on the CLAIM (advocacy), not the nouns. Re-anchored to fire on a recommendation verb near `scapi` (`should/consider/recommend/better off/worth/suggest/advise ... scapi`) OR an imperative move-to-SCAPI with a forward-looking tail (`migrate/move/switch ... scapi ... for new work/going forward/instead`); verified against a 7-phrasing advocacy battery (all fire) + a 7-phrasing correct/declining battery incl. the real run-3 and run-2 answers (all clean), under the real Python `re` engine. Did NOT relax the guard's intent and did NOT touch the skill (the model's behavior is correct); fixed the regex per the CLAUDE.md rule. SKILL.md:207 (stay-in-family) was untouched by this iteration, confirming the behavior is pre-existing.

### The add-coupon timeout was cache-spelunking, not model latency or pure throttle
`synthesis-scenario-add-coupon-checkout` failed 1/5 (run 5, `wall_clock` at 300.4s; runs 1-4 passed 258-278s). The instinctive read ("throttle") was only half right. Transcript decomposition: the >5s wall-clock gaps are all before `user`-role events (tool RESULTS), i.e. tool latency, not model thinking. Two costs stack: (1) cold-cache LIVE scraping of 3 references in the isolated eval HOME (the two biggest gaps, ~36s + ~27s, are the `scenario.js` scrape calls) -- structural to the eval profile, absent in a warm-cache real session; (2) Sonnet SPELUNKING the cache -- run 1 (which passed) still made 13 cache-file reads + 2 `python3 json.load` hand-parses with only 2 `scenario.js` calls; run 5 escalated to `mkdir -p $HOME/.cache`, `ls -R`, and 6 hand-parses before the ceiling cut it off. A fast fixture (createorder) did 0 hand-parses / 4 clean `scenario.js` calls. The spelunk violates the skill's own "scenario.js owns all cache access" Key invariant, roughly doubles wall-clock, and is PRE-EXISTING (both add-coupon runs do it) -- NOT caused by the auth work. Filed as a follow-up (`/c/TODO-scenario-cache-spelunk-adherence.md` + roadmap Parked), NOT fixed here (out of scope for an auth-preamble iteration). The lesson (again, from the certainty-layer post-mortem): don't bank "5/10 = throttle"; read `pass_` per run and root-cause. Deliberately did NOT bump the 300s ceiling -- raising it would mask the spelunk; the real fix is stopping the spelunk (which also cuts the time).

### OCAPI registered-shopper render deferred as a bounded seam
The OCAPI Shop shopper token renders GUEST-only (`{"type":"guest"}`, the resolver's sole output). The registered variant (`{"type":"credentials"}` + a Basic shopper header) would need a signal the plan doesn't carry (`flowSignal` isn't stored on the plan; the OCAPI branch leaves `authFlow` null), so rendering it would breach this iteration's renderer-only surface (touch `b2c-auth-providers.js`/compose, re-verify the 10 routing assertions) -- and the sandbox's `OCAPI_USER_*` creds are a BM user, not a storefront Customer Profile, so it may not even be live-groundable now. Deferred, but NOT lost: it survives as a bounded model-adjustment seam -- a rendered comment on the guest leg naming the swap, a scoped SKILL.md note, and a unit regression guard in `test-auth-render.js` asserting the credentials path stays reachable. Net for OCAPI-registered: "model-composed (capable, non-deterministic)" -> "guest rendered deterministically + one documented adjustment." Tracked: `/c/TODO-ocapi-registered-render.md`.
